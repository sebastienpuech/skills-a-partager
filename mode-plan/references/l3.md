# Phase L3 — pousser la frontière du domaine (V2, opt-in)

> Chargé si `--l3=on`. L3 est la 3e couche du « dépasser la frontière » : après L1 (mécaniques de mode-plan) et L2 (harnais imposé), L3 pousse le **domaine** du skill généré — ce que le modèle ne sait pas encore bien faire *pour cette tâche*, au-delà de la pratique standard.

## Quand
**Uniquement** si `type=skill/agent` ET `ambition=stratégique` (domaine à frontière mouvante). Sur une app jetable ou un skill trivial : **sautée**. Opt-in par flag `--l3=on` (OFF par défaut → comportement inchangé).

## La chaîne (orchestration LLM, via l'écosystème pipeline-plafonds)
```
diagnostic-plafonds  →  labo-recherche  →  [GATE STATIQUE]  →  application-solutions  →  injecté au draft
```
1. **diagnostic-plafonds** : cartographie les vrais plafonds du domaine (contournable-ingénierie / structurel-IA-seule / irréductible). Produit `diagnostic_plafonds.json` (data_model §8).
2. **labo-recherche** : sur les plafonds prouvés, génère des contournements (idéation + transfert analogique + critique adversariale) avec, pour chacun, un `passage_source` (l'évidence sur laquelle il s'appuie) et un `cas_de_test_futur`. Produit `labo_findings.json`.
3. **GATE STATIQUE** (déterministe — `scripts/l3_gate.py`) : voir ci-dessous.
4. **application-solutions** : instancie les trouvailles `injecter` dans le draft (spec §12bis + un cas §10bis par trouvaille).

> La chaîne 1/2/4 est de l'orchestration d'agents (mode-plan les spawne). Le **gate (3)** est le seul morceau déterministe/scriptable — c'est lui qui empêche d'injecter des hallucinations.

## Le gate en deux temps (résout le poule-et-œuf, archi §3)

Au moment du plan, le skill cible n'a **pas encore** de golden set exécutable. Donc :

- **Gate STATIQUE (maintenant, `l3_gate.py`)** — une trouvaille entre au draft SSI :
  - **(a) ancrée** : `is_anchored(passage_source, sources du labo)` — le passage cité existe réellement dans les sources rassemblées (anti-hallucination, réutilise `verify_citations`). Sinon = inventée → `backlog`.
  - **(b) exprimable** : `cas_de_test_futur` non vide — on écrit le futur cas golden §10bis du skill cible en même temps que la techno. Sinon → `backlog`.
  - `injecter` ssi (a) ET (b) ; sinon `backlog spéculatif`. Sortie `l3_gate.json` (data_model §8).
- **Gate DYNAMIQUE (après build du skill cible)** — quand son golden set §10bis existe et tourne, la trouvaille est ré-évaluée : si elle ne bat pas la pratique standard, elle est **retirée**. Le gate L3 n'interroge donc JAMAIS le self-golden-set de mode-plan — il interroge (statiquement puis dynamiquement) le golden set du **skill généré**. *(Reporté : nécessite que le skill cible soit construit.)*

## Contrats (data_model §8)
- `diagnostic_plafonds.json` : `{domaine, plafonds:[{id,type,preuve}]}`
- `labo_findings.json` : `{plafond_id, solutions:[{id,idee,transfert,passage_source,risque_sur_10,cas_de_test_futur}]}`
- `l3_gate.json` : `{plafond_id, gated:[{solution_id,ancree,exprimable_en_golden,decision,raison}], injecter:[], backlog:[]}`

## Usage du gate
```bash
python3 scripts/l3_gate.py --run --case <dossier>   # produit l3_gate.json (sources.md + labo_findings.json)
python3 scripts/l3_gate.py --check                  # mécanisme (CI, evals/l3/)
```
Golden : `evals/l3/L3_1_nutrition/` (1 trouvaille injectable, 1 hallucinée → backlog, 1 vague → backlog).

## Garde-fous
- **Anti-hallucination** : une solution qui cite un `passage_source` absent des sources est rejetée (backlog), pas injectée. C'est le point non-négociable.
- **Anti-injection à l'aveugle** : rien n'entre sans son futur cas golden — on ne pousse la frontière qu'avec le test qui la mesurera.
- **Modèle** : agents L3 sur Opus (comme tout le reste — cf. Gotcha 100% Opus).
